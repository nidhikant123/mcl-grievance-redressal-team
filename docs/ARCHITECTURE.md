# MCL-LRMS: architecture and production roadmap

**MCL Land & Revenue Management & Grievance Redressal System (MCL-LRMS)**

> From acquisition records to identifiable plots, field verification, physical
> possession tracking and transparent grievance redressal, in one integrated platform.

MCL-LRMS is an **AI-assisted decision-support, GIS mapping, land-record
management and grievance-tracking platform**. It never declares ownership, decides
title, declares anyone an encroacher, determines lawful possession, alters
official land records, approves compensation or R&R, or makes final legal
decisions. Final decisions stay with the competent authorities.

This document has two parts:

1. **What is built now**: the demo prototype in this repository (Phase 1).
2. **What production needs**: the full target design, for when MCL IT or a
   vendor takes it forward.

---

## 1. The demo prototype (this repository)

### Why the prototype is simpler than the full design

The MDP team rules (see `CLAUDE.md`) require plain HTML/CSS/JavaScript, no build
step, hosting on Vercel, **one** Supabase table, no login, and **made-up data only**.
The prototype follows those rules. It still demonstrates the complete 19-step
workflow with clearly labelled **DEMO DATA**.

### Pages (maximum 3)

| Page | Who | What it does |
|---|---|---|
| `index.html` | Citizens | Home with the 4 big buttons, Register Grievance, Track Grievance, representation after disposal, About, Services, Notices, Help. English/Hindi toggle. |
| `dashboard.html` | Officers | Demo sign-in (pick a role), KPI cards, charts, filters, universal search, notifications, grievance workflow (assign, schedule field verification, request documents, internal notes, public response, action taken, dispose, reopen), disposal report, 6 reports as PDF or Excel, audit trail, role matrix. |
| `field.html` | Citizens (limited) + officers | Find Acquired Plot (Village → Khata → Plot), GIS map, AI document analysis, AI discrepancy check, Field Verification (GPS, boundary points, polygon, geo-stamped photos), plot status change with mandatory remarks, plot and verification reports. |

Shared files: `style.css`, `common.js` (header/menu, database client, roles,
AI helpers, geometry), `demo-data.js` (fictional plots), `config.js` (Supabase
URL and publishable key only).

### External libraries (all from CDN, no npm)

- Supabase JS v2 (jsDelivr): database access
- Leaflet 1.9 (jsDelivr): map, with OpenStreetMap and Esri satellite tiles
- Chart.js 4 (jsDelivr): dashboard charts
- Tesseract.js 5 (jsDelivr, loaded only when needed): real in-browser OCR

### Database (one table: `lrms_records`)

See `database/01-setup.sql`. A single table holds two kinds of rows:

- `record_type = 'Grievance'`: citizen grievances
- `record_type = 'Plot update'`: field verifications, plot status changes and
  reviewed AI extractions. The newest update for a plot overrides the demo
  baseline in `demo-data.js`.

Safeguards built into the database:

- The **reference number** (`MCL-KA-GRV-2026-000125`, …) is generated by the
  database, never by the browser.
- The **audit trail** (`history` column) is **append-only**. A trigger rejects any
  update that edits or removes an existing entry.
- `id`, `created_at`, `record_type` and `ref_no` cannot be changed after insert.
- Citizens track through the `track_grievance()` function, which returns
  **public fields only**. It never returns internal notes, the mobile number or
  officer names.
- `submit_representation()` lets a citizen reopen a *disposed* grievance only.
- RLS is on. anon/authenticated have select, insert and update, but no delete.

### What AI does in the demo (all output is reviewable)

| AI function | Demo implementation | Real or simulated |
|---|---|---|
| OCR of uploaded scans | Tesseract.js in the browser | **Real** |
| Document classification | Keyword scoring with a confidence value | Real (simple) |
| Field extraction (village, khata, plot, area, notification, dates, names) | Pattern extraction into editable fields, checked against plot records | Real (simple) |
| Boundary line detection | Sobel edge filter on the uploaded scan | Real (simple) |
| Plot-number ↔ boundary association + georeferencing | Pre-computed for the sample map, with 3 ground control points | **Simulated** |
| Discrepancy detection (area, plot no., khata, names) | Rule and similarity checks (Levenshtein) | Real |
| Grievance categorisation and urgency | Keyword model that *suggests* a category | Real (simple) |

AI confidence is always labelled as a **technical indicator, not legal proof**.
Similar names are flagged for manual checking and never treated as the same person.

### Known limits of the demo, stated honestly

1. **No real officer authentication.** The dashboard uses a demo role picker.
   Anyone with the link can open it. **This is acceptable only because all data
   is fictional.** Production must use the authentication design in section 2.3.
2. **The table is readable through the public API key** (team rule: anon SELECT).
   The tracking page shows only public fields, but a technical user could read
   raw rows. Again, this is acceptable only with fictional data.
3. Files: only file names are stored. Field photos are stored as small
   compressed images inside the record.
4. Plot boundaries are drawn on a synthetic grid near the Kaniha area. **They are
   not real parcels.**
5. No SMS/email/OTP gateway, so acknowledgements are shown on screen only.
6. Map tiles come from public OpenStreetMap and Esri services.

## 2. Production design (target)

### 2.1 Components

```
 Citizen app / PWA ─┐                         ┌─ PostgreSQL 16 + PostGIS
 Officer web app  ──┼─ HTTPS ─ API gateway ─ FastAPI backend ─┼─ Object storage (encrypted, S3-compatible)
 Field mobile PWA ──┘   (WAF, rate limits)    │               ├─ Redis (sessions, OTP, rate limits)
                                              │               └─ Audit log store (append-only, hash-chained)
                                              └─ AI worker services (queue):
                                                  OCR (Tesseract/PaddleOCR, Hindi/Odia/English)
                                                  Document classifier + field extractor
                                                  Map vectorisation (line/polygon detection)
                                                  Georeferencing (GCP-based, GDAL)
                                                  Record matching / discrepancy engine
```

- **Frontend:** Next.js (React), with i18n for English, Hindi and Odia, and an
  offline-capable PWA for field users (queue submissions when there is no network).
- **Backend:** Python FastAPI. All business rules, permissions and status changes
  are enforced on the server, never only in the browser.
- **GIS:** PostGIS for geometry. Leaflet or OpenLayers on the client. Base layers
  from an authorised provider (e.g. Bhuvan/NRSC or a licensed satellite source).
  Cadastral layers imported from the State revenue GIS where available.
- **Hosting:** MCL/CIL data centre or a MeitY-empanelled government cloud, with
  data residency in India.

### 2.2 Data model (main tables)

| Table | Key columns |
|---|---|
| `villages` | id, name, tahasil, district, boundary `geometry(MultiPolygon, 4326)` |
| `plots` | id, village_id, khata_no, plot_no, area_acq, area_record, acquired_area, land_type, acquisition_id, compensation_status, rr_status, employment_status, possession_status, demarcation_status, map_availability, plot_status (Green/Yellow/Orange/Red/Blue), boundary `geometry(Polygon)`, boundary_source, ai_confidence, updated_by, updated_at |
| `landholders` | id, plot_id, name, share, relation. Restricted access; PII encrypted. |
| `acquisitions` | id, notification_ref, section, date, award_no, award_date |
| `documents` | id, plot_id?, grievance_id?, type, storage_key, sha256, uploaded_by, classification, ai_confidence, access_level |
| `ai_extractions` | id, document_id, extracted_json, reviewed_json, reviewed_by, reviewed_at, status |
| `field_verifications` | id, plot_id, officer_id, started_at, submitted_at, gps `geometry(Point)`, accuracy_m, boundary `geometry(Polygon)`, result_status, possession, demarcation, remarks |
| `media` | id, verification_id, storage_key, lat, lng, captured_at, officer_id, sha256 |
| `discrepancies` | id, plot_id, type, source_a, source_b, detail, state (open/cleared), cleared_by |
| `grievances` | id, ref_no (unique), applicant fields (PII encrypted), village_id, plot_id?, category, description, language, stage, urgency, assigned_officer_id, assigned_dept, sla_due_at?, public_remarks |
| `grievance_actions` | id, grievance_id, officer_id, action, old_stage, new_stage, note, is_public, created_at |
| `disposals` | grievance_id, category, action_taken, final_remarks, document_id, officer_id, authenticated_via, disposed_at |
| `officers` | id (Officer ID), name, role_id, department, status, pin_hash, pin_set_at, pin_expires_at, failed_attempts, locked_until, mfa_secret_enc |
| `roles`, `permissions`, `role_permissions` | RBAC as in the dashboard "Officers & roles" tab |
| `notifications` | id, officer_id, type, ref, read_at |
| `audit_log` | id, at, officer_id, ip, action, entity, entity_id, old_value, new_value, prev_hash, hash. INSERT-only, no UPDATE/DELETE grants. |

### 2.3 Officer authentication (mandatory for production)

1. **Officer ID → PIN → OTP.** The OTP goes by SMS through an authorised gateway,
   or comes from a TOTP authenticator app.
2. PINs are **individually generated**, shown **once** through a sealed/secure
   channel, and stored only as **Argon2id hashes** with per-user salt. There is
   **no default or universal PIN**, and no credentials in source code.
3. **Lock-out** after 5 failed attempts (time-based unlock plus an admin unlock).
   Per-IP and per-ID **rate limiting**.
4. **PIN expiry/rotation** (e.g. 90 days). PINs can be reset only through an
   authorised administrative procedure, which is logged.
5. Server-side sessions with **15-minute idle timeout**, secure/HttpOnly/SameSite
   cookies, CSRF tokens and re-authentication (PIN + OTP) for disposal.
6. The citizen portal and the officer portal are separate apps on separate
   hostnames. Citizens have no route to officer APIs.

### 2.4 Security checklist

TLS 1.2+ everywhere, encryption at rest (database and object storage),
field-level encryption for PII, parameterised queries/ORM (no SQL injection),
output encoding and CSP (no XSS), CSRF protection, input validation on the server,
file-type and malware scanning for uploads, signed short-lived URLs for documents,
least-privilege database roles, a WAF, daily encrypted backups with tested
restore, CERT-In aligned logging and incident response, and a periodic VAPT
before go-live.

### 2.5 Citizen tracking in production

Reference number + mobile number, then a one-time **OTP** to that mobile.
The citizen sees only the public stage, public remarks and dates. Internal
notes, officer credentials, confidential documents and investigation details
are never sent to the citizen app.

### 2.6 Phased roadmap

| Phase | Scope |
|---|---|
| 1 (done: this demo) | End-to-end workflow with demo data, one table, browser-side AI |
| 2 | Backend with real authentication (Officer ID + PIN + OTP), RBAC, separate tables, secure document storage |
| 3 | Digitise real acquisition schedules and maps for one pilot village. Human review of every AI extraction. |
| 4 | Georeferencing with surveyed ground control points (DGPS). PostGIS layers. Field PWA with offline mode. |
| 5 | SLA configuration, SMS/email via authorised gateway, CPGRAMS/State portal integration if required |
| 6 | Scale to all villages of Kaniha Area, then to other MCL areas |
